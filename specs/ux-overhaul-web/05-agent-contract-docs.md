### 3.1 Signal spec block — REQ-AGENT-01

Canonical content (the four tokens, the line-by-itself rule, the backward-scan rule, and the
no-signal rule), grounded in `signal-parser.ts:27-69` and `runner.ts:677-705`:

```markdown
### Exit Signal (the rauf contract)

End your iteration by emitting exactly one signal token **on a line by itself**:

- `RAUF_DONE` — all acceptance criteria met and verification passed.
- `RAUF_BLOCKED:<reason>` — cannot proceed (missing dependency, conflicting
  requirement); explain why in `<reason>`.
- `RAUF_NEEDS_HUMAN:<reason>` — a human decision or input is required (API key,
  design call); `<reason>` states what is needed.
- `RAUF_REVIEW:<json>` — review pass only: emit a JSON payload of findings
  (matches the `ReviewPayload` schema). Not used in a normal work iteration.

How the runner reads it:

- The runner **scans backwards from the end of your output** and uses the **last**
  signal line it finds. Trailing text after the signal — a commit message, a
  summary, a closing note — does **not** break detection. The token must be the
  whole trimmed line (e.g. a bare `RAUF_DONE`, or `RAUF_BLOCKED:` followed by the
  reason); surrounding prose on the same line is not matched.
- **No signal is never auto-blocked.** If you emit no recognized signal, the runner
  classifies the outcome by exit context (clean exit / non-zero exit / timeout /
  usage-limit), logs the tail of your output for diagnosis, and may reconcile
  already-committed work — it does not silently mark the item blocked.
- Emitting the signal on its own final line is the safest habit, but it does not
  have to be strictly the last line of output (see the backward scan above).
```

Notes for the implementer:
- The "whole trimmed line" detail is exact behavior: `matchSignal` requires `line === "RAUF_DONE"`
  or `line.startsWith("RAUF_<TOKEN>:")` after `.trim()` (`signal-parser.ts:40-68`). Do not imply
  a token embedded mid-sentence will be detected.
- The "never auto-blocked" wording must match CANON §4.5/§4.6 ("no signal → classified by exit
  context, never auto-blocked"). Source: `runner.ts:677-705` — the `none` branch logs the signal
  text and reconciles committed work; it does not call `updateItem(..., {status:"blocked"})`.
- `RAUF_REVIEW:<json>` is the review-only token (it is fired by the review pass, not normal work);
  keep its "review pass only" qualifier so an agent does not emit it during a work iteration.

### 3.2 Model-cascade block — REQ-AGENT-02

Canonical precedence line, grounded in `runner.ts:493-494` + `claude-process.ts:78-79`:

```markdown
### Model Selection

The runner resolves which model drives an iteration by this precedence
(highest wins):

`item.model` > `--model` / run options > project default > provider default

- `item.model` — the selected backlog item's `model` field (per-task override).
- `--model` / run options — the per-run override (`rauf loop run --model …`, or
  the project's configured run options).
- project default — the project's configured default model.
- provider default — if none of the above is set, no model is forced and the
  provider/CLI uses its own configured default.
```

The wording **`item.model > --model/options > project default > provider default`** is mandatory
verbatim (REQ-AGENT-02 / CANON §4.6). Note the *agent-facing* docs surface four tiers (the canon
phrasing splits "run options" and "project default", and names "provider default" for the
fall-through). The existing `docs/SPEC-ARTIFACTS.md` "Model Resolution" section (§85-93) describes
three tiers in code terms; §7.2 reconciles that text to the four-tier canon phrasing so the
machine-facing doc and the agent-facing canon agree.
