### 008 — circuit breaker for consecutive infra failures (2026-06-11)
- **The breaker is load-bearing, not just budget-saving.** Item 007's `uncountIteration("infra_error")` rolls the iteration counter back on every infra death, so the `while (iterationCount < maxIterations)` loop NEVER advances on a persistently broken spawn — without the breaker the loop spins literally forever (proven empirically: hit `consecutive=14343` before being force-cancelled). So the breaker, not `maxIterations`, is what terminates an all-infra run. Tests therefore use a high `maxIterations` (25/100) and assert the breaker — not the budget ceiling — halts it.
- **Halt path mirrors `haltForUsageLimit`.** New `private haltForCircuitBreaker(): "exit"` writes state `error` (via `writeState("error", null, "error", msg)`), emits `loop_error` (the appropriate event for an error halt — exit code ERROR; matches the catch path, and `finish()` in the CLI SSE consumer is idempotent so a single terminal event is right), and writes a DONE summary `error: Circuit breaker: N consecutive infra failures — halting\n<buildSummary>`. The literal `"error: "` prefix is REQUIRED so `parseDoneFileState` (status.ts) classifies the derived status ERROR — the message itself has no `human`/`limit` substring. Returning `"exit"` from `runIteration` makes `start()` return immediately; the `finally` releases the lock.
- **Threshold:** `circuitBreakerThreshold?: number` added to `LoopStartOptionsSchema` (core), `private get circuitBreakerThreshold()` returns `?? 3`. No CLI/web flag (out of scope, like item 007's sleepOnLimit) — configurable programmatically. Logged in the run header via a SEPARATE `appendLog` line (`Circuit breaker threshold: N consecutive infra failures`) — do NOT fold it into the `Loop started (maxIterations=N)` line: `LoopLogPatterns.loopStart` regex (`schemas.ts:298`) is anchored `\(maxIterations=(\d+)\)` and breaks if anything follows the digits before `)`.
- **Counter reset semantics (unchanged from 006, verified):** `consecutiveInfraFailures` resets to 0 on every real outcome (done/blocked/needs_human/timeout/genuine_retry) and increments ONLY on infra_error. usage_limited routes through the usage handler and never touches the counter — so a usage-limit storm sleeps/halts via the usage path, never the infra breaker.
- **Sandbox runtime gotcha (cost me a run):** the dev wrapper runs CLI *source* via bun, but cross-package imports (`@rauf/loop`) resolve to `dist/index.js` (`packages/loop/package.json` `main`). So runner.ts changes are INVISIBLE to `test-sandbox/run.sh`/`verify.sh` until `pnpm build`. The "no build step" claim in CLAUDE.md is true only for same-package CLI edits. Always `pnpm build` before exercising the sandbox after a `packages/loop` change.
- `scenarios/fast-infra-death.sh`: emits a short non-banner text delta then `exit 1` (<10s ⇒ infra_error). verify.sh runs it in the BACKGROUND polling for `state.status==="error"` (kill-guarded against a regressed breaker that would hang), then asserts: state error, item 001 still pending, DONE contains "Circuit breaker", `iteration < 25` (halted before the ceiling), and the run header logged the threshold.

### 009 — reconcile committed work before a non-done outcome (2026-06-11)
- **Recovery placement & gate.** `reconcileCommittedWork(item)` runs in `runIteration` BEFORE the signal switch, gated `if (parsed.signal !== "done")` — so it covers ALL non-done exit classes (blocked/needs_human/timeout/infra/deferred/retry). If `findItemCommit(projectPath, id)` (item 002) returns a hash AND `isTreeClean(projectPath)` is true → mark done, `completedCount++`, push `completedItemIds`, emit `item_completed`, `appendLog("recovered_via_commit: <hash>")`, `writeState("running",null,"clean")`, return "continue". It does NOT call gitCommit again (the commit already exists). `in_progress → done` is a valid transition, so updateItem succeeds.
- **The clean-tree requirement is the false-positive safeguard.** A stale same-id `[rauf] 001:` commit lingers in history (sandbox `.sandbox-git` accumulates them across scenarios; prior `done` runs commit them). Recovery does NOT misfire on those because a non-committing iteration leaves `.rauf/backlog.json` dirty (we set in_progress before spawn) ⇒ `isTreeClean` false ⇒ no recovery. Only an iteration that actually committed everything (`git add -A`, staging the in_progress backlog.json too) yields a clean tree. So clean-tree = "this item's work genuinely landed", which is exactly the recovery signal — no base-range check on the commit needed.
- **isTreeClean depends on runtime files being gitignored.** `git status --porcelain` (item 002's isTreeClean = whole tree) shows untracked `.rauf/state.json`, `rauf.log`, `DONE` as dirty UNLESS ignored — gitCommit's `git add -A` excludes them per-commit, so they stay untracked. Without a gitignore the tree is NEVER clean during a run and recovery can't fire. Fixes: (a) sandbox `setup.sh` now writes the runtime excludes into `.sandbox-git/info/exclude`; (b) the runner.test.ts recovery test writes a `.gitignore` and has the mock `git add -A` commit it. Real projects get this from item 014's installer `.gitignore` work — recovery in production DEPENDS on 014 (degrades safely to current block behavior if absent).
- **Dirty-tree revert gating (the subtle bug).** `revertAbandonedWork` runs AFTER the switch, gated on the item's RESULTING status being `blocked` (re-read via readBacklog) — i.e. only when the item was SET ASIDE (blocked/needs_human/timeout/deferred all end status "blocked") and the loop moves to a DIFFERENT item. Outcomes that leave the item PENDING (infra_error, usage retry, mid-retry) retry the SAME item and MUST NOT revert. First attempt gated on `parsed.signal !== "done"` (revert on every non-done) — that reverted on infra_error and stashed the item-007 test's untracked `attempt-count` counter file, so its retry re-read n=0 and never succeeded (completedCount 1→0). Lesson: infra_error is a fast environmental death that did NO work; there's nothing of THIS iteration's to revert, and wiping the tree there breaks same-item retries.
- **Revert preserves loop bookkeeping.** `git stash push --include-untracked -m "rauf: abandoned work from item <id>" -- . ':(exclude,glob)**/.rauf/**' ':(exclude,glob)**/backlog.json' ':(exclude,glob)**/backlog.json.bak'`. A `git status --porcelain --` pre-check over the SAME pathspecs short-circuits to a no-op when only bookkeeping is dirty — so in all existing sandbox scenarios (mocks write NO work-tree code; only backlog.json/.rauf churn) the revert never fires and can't regress them. Stash (not `reset --hard`) because reset --hard is whole-tree and would wipe the uncommitted backlog.json status the loop relies on as its on-disk source of truth (it's only committed on the NEXT done). `:(exclude)` pathspecs keep .rauf/ and backlog.json wherever they live (default root `.rauf/backlog.json` vs multi-backlog `specs/<f>/backlog.json`).
- **Sandbox scenario `commit-no-signal.sh`:** mock emits a text delta, writes a file, `git add -A` (with the runtime excludes) + `git commit -m "[rauf] 001: recovered via commit"`, then exits with NO RAUF_DONE. verify.sh asserts item 001 done + log `recovered_via_commit` + NOT blocked/deferred. Added as the LAST scenario so its accumulated `[rauf] 001:` history can't bleed into earlier non-recovery scenarios (belt-and-suspenders with the clean-tree safeguard). Standalone `run.sh commit-no-signal` writes `recovered-feature.txt` into the work tree (GIT_WORK_TREE=test-sandbox) — clean it up so it doesn't leak into the parent commit.

### 010 — right-size maxIterations from the backlog (2026-06-11)
- New pure core module `packages/core/src/budget.ts` exports `computeMaxIterations(backlog, {safety?, retryHeadroom?})` → `{cap, pending, avgIters, needed}` plus `formatBudgetMath(estimate, safety?)`. Formula: `needed = ceil(pending * avgIters * safety) + retryHeadroom` (safety 1.5, retryHeadroom 5); `cap = max(20, needed)` ONLY when pending>0 — empty/no-pending returns `{cap:0,...}` so callers fall back to the flat `DEFAULT_MAX_ITERATIONS=20`. avgIters = mean of pending items' `estimatedIterations ?? 1`. **Math.ceil wraps the whole scaled product**, not just safety — test gotcha (ceil(1*1*1.5)=2, not 1.5).
- CLI `handleLoopRun`: `const iterations = iterationsFlag ?? deriveMaxIterations(paths)`. New helper `deriveMaxIterations(paths)` reads the backlog, returns 20 on read-fail or pending===0, else logs `info(c.dim(formatBudgetMath(estimate)))` and returns `estimate.cap`. Explicit `--iterations` still wins (the `??`).
- CLI `handleLoopStart` (server mode): when `--iterations` omitted, resolve backlog root+paths, read, compute, `info(formatBudgetMath)` + set `body.maxIterations = cap` — done CLI-side because the detached server can't write to the user's terminal. ### 020 — hold the loop lock across reset/resume recovery (close TOCTOU race) (2026-06-11)
- **The race:** `guardLoopLock` was check-only (checkLock → refuse-if-alive / clear-if-stale) and returned WITHOUT holding any lock; then `recoverInterruptedLoop` mutated backlog/state. A concurrent `rauf loop run` could `acquireLock` and start in that gap. Fix = actually HOLD the lock across the mutation window.
- **Replaced `guardLoopLock`/`LockGuard` in recovery.ts with two helpers** (only callers were reset/resume): `acquireRecoveryLock(paths): Result<{cleared}>` and `releaseRecoveryLock(paths): Result<void>`. acquireRecoveryLock does a `checkLock` ONLY to report whether a stale lock was cleared (for the "Cleared a stale loop lock" message + reset's `lockCleared` JSON field), then defers to core `acquireLock` as the authoritative atomic gate — so a live lock that appears between the check and the acquire still yields LOCK_CONFLICT. Reuses core checkLock/acquireLock/releaseLock; no reimplemented PID checks.
- **Owner-aware release** (`releaseRecoveryLock`): checkLock first; if the lock is present, not stale, and `pid !== process.pid` it's a live DIFFERENT process's lock → return ok WITHOUT unlinking. Otherwise (our pid, or stale, or absent) → core `releaseLock`. Belt-and-suspenders: on a LOCK_CONFLICT refuse we never enter the try/finally so release is never even called on someone else's lock.
- **reset (reset-commands.ts):** acquire → if `!ok && code===LOCK_CONFLICT` refuse `ExitCode.CONFLICT` (now uses `ErrorCodes.LOCK_CONFLICT`, was `CONFLICT`) with no mutation; else own the lock and `try { recoverInterruptedLoop } finally { releaseRecoveryLock }`. `lockCleared` now comes from `acquired.value.cleared`.
- **resume (resume-commands.ts):** must release BEFORE relaunch (the loop's own entrypoint re-acquires). Structure: acquire → `let relaunch=false; let exitCode; try { detect + recover + eligibility-decide, setting exitCode on early returns / relaunch=true otherwise } finally { releaseRecoveryLock(paths) }` → `if (!relaunch) return exitCode;` → build runCtx + `runLoop`. The finally frees the lock before the relaunch runs, and on any throw. All the early-exit branches (nonDone===0, recovery error, no-eligible-item) set `exitCode` instead of returning directly so the finally always runs while still holding the lock during the read of post-recovery backlog.
- **Tests:** existing live-lock tests (lock pid = `process.pid`, alive) already assert reset/resume refuse with CONFLICT + no mutation — they now exercise the acquire-refuse path unchanged. New `packages/cli/src/recovery.test.ts` unit-tests the helpers directly: acquire (none→cleared:false+our pid / stale→cleared:true+our pid / live→LOCK_CONFLICT+lock intact) and release (own→removed / absent→noop / stale→removed / **live different pid via a real `spawn(process.execPath, ['-e','setTimeout…'])` child → NOT deleted**). A guaranteed-alive distinct PID needs a real child process (processStartTime:null ⇒ isProcessRecycled=false ⇒ reads alive).
